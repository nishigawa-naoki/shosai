# 区切りごとのレビュー

実装の区切り（ひとつの機能・修正が動く状態になってコミットした時点）で、完了報告の前に必ず実行する。
レビューは**必ずサブエージェントで行う**。実装した本人（メインのエージェント）の意図や思い込みを持ち込まないため。

## 1. 範囲を決める

1. 作業中の変更をすべてコミットする
2. 前回レビュー済みの位置を確認する: `git rev-parse --verify -q last-review`
   - タグがあれば、範囲は `last-review..HEAD`
   - なければ、リポジトリ全体が対象（初回）

## 2. サブエージェントに依頼する

`Agent` ツールで `general-purpose` を起動する。プロンプトは下のテンプレートに、`{…}` の部分だけを埋めて渡す。

**プロンプトに入れてはいけないもの**（先入観を与えないため）
- 実装の意図や「こう考えてこう作った」という説明
- 「ここは確認済み」「テスト済み」「問題ない」といった主張
- 過去のレビュー結果や、既知の問題のリスト
- 特定の箇所に注目させる誘導

入れてよいのは、リポジトリの場所、対象の範囲、アプリが何をするものかの一行説明、観点のチェックリスト、出力形式だけ。

```
あなたはコードレビュアーです。以下のリポジトリの変更を、独立した視点でレビューしてください。

- リポジトリ: {リポジトリの絶対パス}
- 対象: {`git diff last-review..HEAD` で見える変更 / リポジトリ全体}
- アプリの概要: {一行。例: スマホ・PC 両用の個人向け執筆 PWA（React + CodeMirror 6 + Firebase Auth/Firestore）}

## ルール
- 読み取り専用です。リポジトリ内のファイルを編集・作成・削除したり、コミットしたりしないでください
- 差分だけでなく、関係する周辺のコード・設定ファイル（Firestore ルール、ホスティング設定、依存パッケージなど）も読んでください
- 必要ならビルド・lint を実行したり、リポジトリの外の一時ディレクトリで検証用スクリプトを動かしたりして構いません
- 推測ではなく、具体的な入力・状態・操作の順序で「何が起きるか」を示せるものだけを指摘してください。好みの問題やコードスタイルは不要です

## 観点

### セキュリティ
- 認証・認可：クライアントのコードとサーバー側のルール（Firestore ルールなど）が一致しているか。他人のデータに触れる経路がないか
- XSS や HTML の差し込み（innerHTML、Markdown の描画、URL の扱い）
- オープンリダイレクト、パスの組み立てへの外部入力の混入
- 秘密情報のコミット、端末内に残るデータ、ログへの機微情報の出力
- HTTP ヘッダー、Service Worker のキャッシュ
- 依存パッケージ：本番のバンドルに実際に入るものの既知の脆弱性

### 動作・バグ
- 競合状態：自動保存、他端末からの更新とローカル編集のぶつかり合い、オフライン↔オンラインの切り替わり
- useEffect の依存配列・後片付け漏れ、古いクロージャ、購読の解除漏れ
- 境界値：空文字、非常に長い文章、サロゲートペア・絵文字、日本語 IME の変換中の入力
- 書き込みの失敗・Promise の放置、エラー時に利用者に何が見えるか
- データが失われる操作の順序（画面遷移・タブを閉じる・削除・ログアウト）
- スマホ特有の挙動（ソフトウェアキーボード、PWA としての起動、バックグラウンド化）

### 冗長性
- 重複したロジック、使われていないコード・依存パッケージ
- 不要な再レンダリング、購読のやり直し、Firestore への余計な読み書き（料金に直結する）
- 目的に対して過剰な抽象化、もっと単純に書ける処理

## 出力形式
重大度の高い順に、指摘ごとに以下を書いてください。
- 観点（セキュリティ / バグ / 冗長性）と重大度（高 / 中 / 低）
- 場所（ファイルパス:行番号）
- 問題の内容（1〜2文）
- 起きる状況（具体的な入力・状態・操作の順序と、その結果）
- 修正案

最後に「確認したが問題なしと判断した点」を箇条書きで簡潔に挙げてください。
```

## 3. 指摘を検証する

サブエージェントの指摘をそのまま信じない。1件ずつ自分でコードを読み、可能なら再現して、次のどれかに分類する。
- **確定**：実際に起きる → 修正する
- **却下**：前提が誤っている、または起きない → 理由を記録する
- **要相談**：仕様の判断が必要、または修正の影響が大きい → ユーザーに聞く

## 4. 修正する

- 確定した指摘を修正し、ビルド・lint を通し、必要ならブラウザで動作を確認してからコミットする
- 修正が大きい場合は、修正した差分だけを対象に、新しいサブエージェントでもう一度レビューする（同じテンプレート、先入観なし）

## 5. 区切りを記録する

```sh
git tag -f last-review HEAD
```

## 6. 報告する

ユーザーには日本語で、以下を簡潔に伝える。
- 指摘の一覧と、それぞれの結果（修正した / 却下した（理由） / 相談したい）
- 修正の内容と、その確認方法
- サブエージェントが「問題なし」とした主な点（1〜3行）
